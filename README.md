# Brain — «второй мозг» для Obsidian

Индексирует внешние Obsidian-хранилища: каждая заметка дистиллируется через OpenAI-совместимое API в карточку (summary, ключевые слова, сущности, вопросы, тип) и чанки по заголовкам, хранится в SQLite с FTS5 и отдаётся чату через MCP-сервер `brain`. Дополнительно строится связность: заметки с общими тегами (а при их отсутствии — по общим keywords/entities) сравниваются ИИ по готовым саммари, а найденные связи (`score`, общие темы) возвращаются при поиске. Существующие заметки код не изменяет; опциональная запись создаёт только новые файлы в `Telegram/`.

## Быстрый старт

Нужны Python 3.10+ и любой OpenAI-совместимый API (OpenAI, OpenRouter, Ollama, LM Studio, vLLM…).

```bash
pip install -r requirements.txt
copy .env.example .env     # Windows; на Linux/macOS: cp .env.example .env
# заполни .env — см. ниже
python sync.py --dry-run   # показать, что будет проиндексировано, без вызовов LLM
python sync.py             # построить индекс
```

В `.env` обязательны:

- `VAULT_PATH` — путь к хранилищу Obsidian. Можно несколько через `;`, пути могут быть относительными (считаются от каталога с кодом). Корень файловой системы (`/`, `C:\`) указывать нельзя:

  ```
  VAULT_PATH=../Obsidian Git;../Obsidian Personal
  ```

- `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` — параметры API-сервера.

Все остальные настройки (`LLM_TIMEOUT`, `LLM_JSON_MODE`, `LLM_MAX_INPUT_CHARS`…) расписаны комментариями в `.env.example`.

Первый прогон делает LLM-вызов на каждую заметку — при большом хранилище это заметные время и расходы. Дальше инкрементально по SHA-256: пересобираются только новые/изменённые заметки. Заметки больше `LLM_MAX_NOTE_BYTES` (по умолчанию 5 МБ) пропускаются, а map-reduce делает не больше `LLM_MAX_CHUNKS` (60) вызовов на заметку — это защита от случайного файла-гиганта и лишних расходов. После индексации могут выполняться дополнительные LLM-сравнения пар заметок с общими тегами — не больше `BRAIN_LINK_MAX_PAIRS` (100) за прогон; подробности и отключение — в разделе «Связность заметок».

### Права на секреты и индекс

`data/brain.db` содержит полный текст заметок, а `.env` — ключ API. Юниты systemd выставляют `UMask=0077`, но для уже созданных файлов на Linux один раз выполни:

```bash
chmod 700 data
chmod 600 .env data/brain.db*
```

Симлинки и junction внутри хранилища не индексируются: ссылка не может вытащить в индекс (и в LLM) файл снаружи хранилища.

## Подключение к чату (MCP)

Индекс должен быть уже построен. MCP открывает `data/brain.db` только на чтение (`mode=ro` + `PRAGMA query_only=ON`) и не выполняет DDL/WAL; если БД ещё нет, инструменты вернут ошибку «БД ещё не создана». У WAL-базы read-only подключению нужен доступ на запись к `-shm` (или к каталогу `data/`), поэтому MCP проще запускать тем же пользователем, что и `sync.py`; отдельному пользователю только на чтение может понадобиться запись в `data/` для `-shm`.

MCP не вызывает LLM, поэтому не подхватывает `LLM_API_KEY` из `.env` и удаляет его из своего окружения. `search_notes` обрезает запрос до 500 символов и `k` до 50; `get_note` отдаёт только обычные файлы до 1 МБ (для больших — `get_chunk`). Зарегистрируй сервер в MCP-клиенте (клиент запускает его сам), например `.mcp.json` для Claude Code:

```json
{
  "mcpServers": {
    "brain": {
      "command": "python",
      "args": ["<путь к репозиторию>/mcp_server.py"]
    }
  }
}
```

В OpenCode — секция `mcp` в `opencode.json`. Инструменты: `search_notes` (поиск по карточкам и фрагментам; в каждой карточке до 3 связанных заметок), `get_chunk` (фрагмент по id), `get_note` (полный текст заметки), `get_related` (связанные заметки по пути), `list_notes` (список по типу), `brain_status` (только числовые счётчики: заметки, фрагменты, теги, оценённые связи и очередь неоценённых пар — без путей и текста). У `search_notes` есть `include_related=false`, если связи не нужны в ответе.

## Обновление индекса

- `python sync.py` — разовый инкрементальный прогон;
- `python sync.py --reindex` — принудительно переобработать все заметки, игнорируя SHA-256 (например после смены LLM-модели); старые карточки и их связи заменяются;
- `python sync.py --rebuild-links` — удалить все оценки и счётчики ошибок связей и пересчитать пары заново; вместе с `--reindex` даёт полный пересчёт после смены модели (`python sync.py --reindex --rebuild-links`);
- `python sync.py --watch` — следить за хранилищами и переиндексировать на лету (не подходит для хранилищ, смонтированных по NFS/SMB — события файловой системы туда не доходят);
- Linux-сервер: готовые примеры — `brain-sync.service` (демон `--watch`) или `brain-pull.timer` + `brain-pull.service` (раз в 5 минут: `git pull` хранилища + `sync.py`). Установка описана в комментариях внутри файлов.

Установка юнитов (Linux, от root):

```bash
sudo ./install-systemd.sh sync    # brain-sync.service
sudo ./install-systemd.sh pull    # brain-pull.service + brain-pull.timer
sudo ./install-systemd.sh         # все файлы
```

Скрипт копирует файлы в `/etc/systemd/system` и делает `systemctl daemon-reload`; включение и запуск — вручную (`systemctl enable --now ...`). Варианты `sync` и `pull` взаимоисключающие, включайте один.

Индекс — `data/brain.db` (в git не попадает). После смены LLM-модели пересоберите карточки и связи без удаления файла: `python sync.py --reindex --rebuild-links` (прогон платный — LLM-вызов на каждую заметку). Удалять `data/brain.db` нужно только при несовместимом изменении схемы. Новые таблицы и аддитивные колонки (`note_tags`, `note_links`, `link_failures`, `note_links.shared_terms`) создаются автоматически, пересборка для них не нужна.

## Журнал ошибок

Предупреждения и ошибки `sync.py` и `mcp_server.py` дополнительно пишутся в ротирующий файл `data/errors.log` (по умолчанию, `LOG_FILE=auto`) — каталог `data/` под systemd уже разрешён к записи. В консоль/journald привычный вывод не меняется; в журнале остаётся компактный журнал сбоев с уровня `LOG_FILE_LEVEL` (по умолчанию `WARNING`) и выше: файлы-пропуски, ошибки индексации заметок и связей, стадии ошибок `create_note` (без путей и текста заметок). `LOG_FILE=off` оставляет только stderr; вместо `auto` можно указать путь (лучше абсолютный). Ротация: 5 МБ × 3 резервные копии.

### Ошибки сравнения связей

`ValueError: в ответе модели нет JSON-объекта` с пустым или обрезанным ответом означает, что LLM не вернула JSON: чаще всего исчерпан `LLM_LINK_MAX_TOKENS` (reasoning-модели тратят его на рассуждение), сработал фильтр провайдера или пришёл пустой `content`. Пара при этом **не сохраняется** и не считается оценённой: она остаётся в очереди и будет повторена. Ошибка одной пары не мешает остальным и не портит уже сохранённые связи; после `BRAIN_LINK_MAX_ATTEMPTS` ошибок ответа модели пара откладывается, чтобы не блокировать очередь, а `--rebuild-links` возвращает её в работу. Прогон завершается с кодом 1, если были ошибки заметок или связей.


## Связность заметок

Связи строятся в два этапа, чтобы не сравнивать через LLM каждую пару заметок:

1. **Общие теги.** Из заметки извлекаются теги Obsidian: `tags`/`tag` во frontmatter и инлайновые `#теги` (код, ссылки и заголовки не считаются). Теги нормализуются к нижнему регистру. Кандидатами становятся пары с хотя бы одним общим тегом; редкие теги весят больше, а теги, встречающиеся чаще `BRAIN_LINK_MAX_TAG_FANOUT` заметок, пропускаются.
   Если у заметки нет пары по тегам, включается fallback по общим `keywords`/`entities` из её карточки: нужно не меньше `BRAIN_LINK_MIN_SHARED_TERMS` (по умолчанию 2) общих термина, а термины, встречающиеся чаще `BRAIN_LINK_MAX_TERM_FANOUT` заметок, пропускаются. Fallback не используется, если у заметки уже есть теговая пара-кандидат.
2. **Сравнение саммари.** Для каждой пары-кандидата один LLM-запрос сравнивает уже готовые `summary` карточек (если заметка ещё не индексирована — сначала обычный `sync.py`). Модель возвращает `score` от 0 до 1, общие темы и короткое объяснение. Результат кэшируется в `note_links`; при изменении или удалении заметки все её пары удаляются и пересчитываются. Если модель вернула пустой или обрезанный ответ, запрос повторяется с удвоенным лимитом токенов (`LLM_LINK_RETRIES`, по умолчанию 1). После `BRAIN_LINK_MAX_ATTEMPTS` (по умолчанию 3) ошибок ответа подряд пара откладывается в `link_failures`, чтобы не занимать очередь каждый прогон; `sync.py --rebuild-links` сбрасывает и оценки, и счётчики.

За один прогон выполняется не больше `BRAIN_LINK_MAX_PAIRS` (по умолчанию 100) сравнений; на заметку — не больше `BRAIN_LINK_MAX_PER_NOTE` сильных связей. Остальное досчитается в следующие прогоны. Отключить этап целиком: `BRAIN_LINKS_ENABLED=0` (теги при этом всё равно обновляются, это локальная операция без LLM).

Порог выдачи в MCP — `BRAIN_LINK_MIN_SCORE` (по умолчанию 0.65). `search_notes` добавляет к карточке до 3 связанных заметок с `score`, `shared_tags`, `shared_terms` и `common`; `get_related(path, k, min_score)` отдаёт связи по одной заметке. Таблицы `note_tags` и `note_links` создаются при обычном `connect()`: старую БД не нужно пересобирать только ради тегов/связей, `sync.py` сам заполнит теги и постепенно построит связи. После смены LLM-модели запустите `python sync.py --reindex --rebuild-links`.

## Приватность

Содержимое заметок отправляется в настроенный LLM API. Для чувствительных данных подними локальный сервер (Ollama, LM Studio, vLLM) и укажи его в `LLM_BASE_URL`. Сравнение заметок для связей отправляет только готовые `summary` и теги, но первичная индексация всё равно отправляет текст заметки.

`LLM_BASE_URL` вне `localhost`/`127.0.0.1`/`::1` должен быть HTTPS: по HTTP ключ и текст заметок идут открытым текстом. Для LAN-сервера по HTTP нужно осознанно задать `LLM_ALLOW_HTTP=1` (будет предупреждение в stderr).

## Безопасность

- **Заметки — недоверенные данные.** `search_notes`, `get_chunk`, `get_note` и `get_related` возвращают текст из хранилища или его производные (саммари, темы, объяснения модели); заметка может содержать инструкции для агента (prompt injection). В MCP-клиенте не включай автоподтверждение опасных инструментов и не давай этому серверу лишних прав. Особенно это касается авто-pull’нутых клиппингов и чужих материалов.
- **MCP не аутентифицирует клиента.** Любой процесс, которому разрешён запуск сервера, видит весь индекс. По умолчанию транспорт stdio и сеть не слушается; при запуске по HTTP нужен внешний auth-прокси.
- **Авто-pull хранилища — это доверие к remote.** `brain-pull.timer` и Obsidian Git тянут не только заметки, но и `.mcp.json`, `.obsidian/plugins`; скомпрометированный remote может подменить команду MCP или подсунуть плагин. Для сервера — read-only deploy key/PAT, 2FA и branch protection; не открывай авто-pull’нутое хранилище в клиенте с автозапуском MCP; `.mcp.json` лучше держать вне хранилища или проверять изменения; community plugins — restricted mode.

## Запись из Telegram-бота

MCP-инструмент `create_note(content, request_id, title="", tags=None)` создаёт **только новые**
Markdown-файлы в `Telegram/` первого хранилища. Существующие заметки не меняются.
Для включения передайте `BRAIN_WRITE_ENABLED=true` в `env` MCP-сервера
в `.mcp.json` (или в окружении процесса). По умолчанию запись выключена, и
`create_note` вообще не регистрируется в списке инструментов (нужен перезапуск
MCP-сервера после смены переменной).
Если конфиг закреплён SHA-256, после изменения обновите пин на стороне клиента.

Клиент обязан проверять права: в KapumChatBot запись доступна только `OWNER_IDS`
в личке через намерение «запомни», выбор после форварда или кнопку под ответом.
Обычная модель чата не получает инструмент записи. Чтение в этом боте открыто
всем пользователям диалога: не подключайте к нему закрытые заметки.

`request_id` — стабильный идентификатор действия клиента (до 200 символов):
повтор с тем же текстом не создаёт дубликат, другой текст с тем же ID отклоняется.
Он должен быть глобально уникальным и содержать namespace пользователя/чата
(например, `tg:<chat_id>:<message_id>`): сервер не аутентифицирует клиента, и
совпадение с чужой записью вернёт конфликт.
Текст ограничен 100000 символами. Клиент может передать понятное имя `title`
и до 8 ключевых тегов `tags` (KapumChatBot подбирает оба поля одним коротким
AI-запросом; сам MCP-сервер по-прежнему не вызывает LLM). Имя файла без `.md`,
**включая** суффикс request_id и возможный счётчик коллизии, содержит только
русские/латинские буквы и цифры и занимает до 48 символов. Пустое/непригодное
имя заменяется словами из первой строки либо «Заметка». Файл создаётся
эксклюзивно: занятые имена не перезаписываются, даже при коллизии суффикса.

В YAML frontmatter записываются `title`, ключевые `tags` и полный хеш действия
`brain_request_id`; исходный текст сохраняется ниже без пересказа. Теги из
исходного frontmatter/текста также сохраняются и сразу попадают в `note_tags`,
`keywords` и FTS. Повтор с новым AI-именем/тегами находит прежний файл по
идентификатору и сохраняет его метаданные даже при недоступном индексе.
Старые SHA-256-файлы распознаются без переименования или дописывания тегов.
Для передачи метаданных нужно обновить клиент и MCP-сервер и перезапустить MCP.

Новая заметка сразу индексируется в SQLite/FTS без
платного LLM; обычный sync сохраняет её по тому же content_hash. Если индекс
временно недоступен, файл остаётся для безопасного повтора или последующего sync.
Сохраняется текст/подпись сообщения, не бинарное вложение. Индексация
идемпотентна: если `sync.py` успел проиндексировать файл первым, запись
продолжается к commit/push, а не падает с `UNIQUE constraint failed`. Ошибки
стадий возвращаются не через `isError`, а обычным dict:
`{"git_pushed": false, "error": "stage=file|index|git|validate|internal: <Type>"}`.
Клиент обязан считать это ошибкой, даже если MCP-транспорт считает вызов
успешным. Пути и текст заметки в код стадии не попадают.

### Синхронизация перед записью

Перед созданием файла `create_note` делает `git fetch --prune` и пытается
fast-forward текущей ветки на upstream. Если pull невозможен из-за локальных
изменений или расхождения веток, **origin считается главным**: выполняется
`git reset --hard @{upstream}`. Локальные изменения tracked-файлов и локальные
коммиты при этом теряются; untracked-файлы удаляются только там, где origin уже
содержит такой путь. Если не удалось даже получить origin (сеть, авторизация,
upstream), заметка **не создаётся**, а клиент получает `stage=sync` с безопасной
причиной: аутентификация, SSH host key/ключ, DNS, сеть, upstream или Git lock.

Это осознанно выбранная политика: рассинхронизация хранилища всегда решается
в пользу origin. Не держите в серверном клоне несохранённые правки, которые
нельзя потерять.

### Автоматическая публикация в Git

После индексации `create_note` коммитит **только созданный файл** и выполняет
обычный push в upstream текущей ветки. Успех возвращается только после push
(`git_pushed=true`). Отдельного переключателя нет: включённая запись требует Git.

Первое хранилище должно быть корнем Git-клона с настроенным upstream. От имени
пользователя MCP-сервера настройте `user.name`, `user.email` и SSH-ключ/credential
helper **с правом записи** в remote (read-only deploy key больше не подходит).
Пароли интерактивно не запрашиваются. Корень хранилища, `.git` и `Telegram/`
должны быть доступны этому пользователю для записи. Секреты не добавляйте в код
или URL remote; используйте SSH/credential helper.

Identity лучше задать **локально в репозитории хранилища**: MCP-процесс в
systemd может не видеть `~/.gitconfig` из-за `ProtectHome=true`.

```bash
sudo -u brain git -C '/opt/brain-vault' config user.name 'Kapum ChatBot'
sudo -u brain git -C '/opt/brain-vault' config user.email 'bot@example.com'
```

Укажите свой GitHub-email или noreply-адрес. Если remote доступен по SSH,
ключ тоже должен быть доступен процессу вне `/home` (например, deploy key в
`/etc/kapum-chatbot/` и `GIT_SSH_COMMAND`), иначе push из MCP не пройдёт
аутентификацию, хотя ручной запуск doctor из обычной оболочки будет успешным.

- Чужие staged/unstaged-файлы не затрагиваются: коммит строится отдельным индексом,
  Git-хуки не запускаются. Пушится точный SHA, только в upstream-ветку, без тегов
  и рекурсивной публикации submodules, без force.
- При наличии посторонних локальных коммитов автоматический push запрещён,
  чтобы не отправить их вместе с заметкой. Сначала разберите их вручную.
- Если remote ушёл вперёд или ветки разошлись, автоматического merge/rebase нет:
  синхронизируйте клон вручную (например, `git pull --ff-only`, если возможен),
  затем повторите исходное сохранение. `brain-pull.timer` продолжает использовать
  fast-forward и не разрешает расхождение истории автоматически.
- При ошибке Git файл и индекс остаются локально. Повтор с тем же `request_id`
  повторяет публикацию без нового файла/коммита; в боте повторите ту же кнопку.
  Уже закоммиченная, но не отправленная заметка тоже корректно отправляется при
  повторе. Пока она не отправлена, сохранение другой заметки не будет пушить её
  попутно: сначала повторите неудавшееся действие.
- Записи одного MCP-процесса сериализованы; смена HEAD другим процессом не
  перезаписывается. Каждый Git-процесс ограничен 60 секундами; таймаут записи
  в Telegram-клиенте — не менее 180 секунд.

Ошибки Git содержат название стадии и безопасную категорию: например,
`Ошибка Git (commit-tree): не настроены user.name/user.email` или
`Ошибка Git (fetch): сбой DNS Git`. Полный stderr не возвращается: он может
содержать credentials в remote URL и приватные пути. Клиент KapumChatBot
распознаёт эти категории и добавляет подсказку в traceback; для этого нужно
обновить обе стороны и перезапустить MCP-процесс.

Не включай `BRAIN_WRITE_ENABLED=true` для MCP-профиля общего чата или модели,
которая видит недоверенные заметки: prompt injection может инициировать запись.
Права проверяет клиент.

### Проверка готовности записи

На сервере запустите скрипт **тем же пользователем и с теми же переменными**,
что у MCP-сервера (особенно `VAULT_PATH` и `BRAIN_WRITE_ENABLED`):

```bash
cd /opt/ObsidianBrain
BRAIN_WRITE_ENABLED=true .venv/bin/python write_doctor.py
# при необходимости проверить доступ к remote:
BRAIN_WRITE_ENABLED=true .venv/bin/python write_doctor.py --network
```

Скрипт проверяет флаг записи, права на хранилище/`Telegram`/SQLite/`.git`,
корень Git-репозитория, ветку, upstream, `user.name`/`user.email`, staged-файлы,
отставание клона от upstream и локальные коммиты. `--network` делает `git fetch`
и показывает, если клон отстал или ветки разошлись; автоматический merge/rebase
не выполняется. Секреты, remote URL и заметки не печатаются.
Если `.mcp.json` задаёт `BRAIN_WRITE_ENABLED` только для MCP-процесса, doctor
запускайте с этой переменной явно.

Проверка на временных файлах без `.env`, LLM и реального хранилища:
`python -m unittest discover -s tests -v`.
