# Brain — «второй мозг» для Obsidian

Индексирует внешние Obsidian-хранилища: каждая заметка дистиллируется через OpenAI-совместимое API в карточку (summary, ключевые слова, сущности, вопросы, тип) и чанки по заголовкам, хранится в SQLite с FTS5 и отдаётся чату через MCP-сервер `brain`. Существующие заметки код не изменяет; опциональная запись создаёт только новые файлы в `Telegram/`.

## Быстрый старт

Нужны Python 3.10+ и любой OpenAI-совместимый API (OpenAI, OpenRouter, Ollama, LM Studio, vLLM…).

```bash
pip install -r requirements.txt
copy .env.example .env     # Windows; на Linux/macOS: cp .env.example .env
# заполни .env — см. ниже
python sync.py --dry-run   # показать, что будет проиндексировано, без вызовов LLM
python sync.py             # построить индекс
```

В `.env` обязательны:

- `VAULT_PATH` — путь к хранилищу Obsidian. Можно несколько через `;`, пути могут быть относительными (считаются от каталога с кодом). Корень файловой системы (`/`, `C:\`) указывать нельзя:

  ```
  VAULT_PATH=../Obsidian Git;../Obsidian Personal
  ```

- `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` — параметры API-сервера.

Все остальные настройки (`LLM_TIMEOUT`, `LLM_JSON_MODE`, `LLM_MAX_INPUT_CHARS`…) расписаны комментариями в `.env.example`.

Первый прогон делает LLM-вызов на каждую заметку — при большом хранилище это заметные время и расходы. Дальше инкрементально по SHA-256: пересобираются только новые/изменённые заметки. Заметки больше `LLM_MAX_NOTE_BYTES` (по умолчанию 5 МБ) пропускаются, а map-reduce делает не больше `LLM_MAX_CHUNKS` (60) вызовов на заметку — это защита от случайного файла-гиганта и лишних расходов.

### Права на секреты и индекс

`data/brain.db` содержит полный текст заметок, а `.env` — ключ API. Юниты systemd выставляют `UMask=0077`, но для уже созданных файлов на Linux один раз выполни:

```bash
chmod 700 data
chmod 600 .env data/brain.db*
```

Симлинки и junction внутри хранилища не индексируются: ссылка не может вытащить в индекс (и в LLM) файл снаружи хранилища.

## Подключение к чату (MCP)

Индекс должен быть уже построен. MCP открывает `data/brain.db` только на чтение (`mode=ro` + `PRAGMA query_only=ON`) и не выполняет DDL/WAL; если БД ещё нет, инструменты вернут ошибку «БД ещё не создана». У WAL-базы read-only подключению нужен доступ на запись к `-shm` (или к каталогу `data/`), поэтому MCP проще запускать тем же пользователем, что и `sync.py`; отдельному пользователю только на чтение может понадобиться запись в `data/` для `-shm`.

MCP не вызывает LLM, поэтому не подхватывает `LLM_API_KEY` из `.env` и удаляет его из своего окружения. `search_notes` обрезает запрос до 500 символов и `k` до 50; `get_note` отдаёт только обычные файлы до 1 МБ (для больших — `get_chunk`). Зарегистрируй сервер в MCP-клиенте (клиент запускает его сам), например `.mcp.json` для Claude Code:

```json
{
  "mcpServers": {
    "brain": {
      "command": "python",
      "args": ["<путь к репозиторию>/mcp_server.py"]
    }
  }
}
```

В OpenCode — секция `mcp` в `opencode.json`. Инструменты: `search_notes` (поиск по карточкам и фрагментам), `get_chunk` (фрагмент по id), `get_note` (полный текст заметки), `list_notes` (список по типу).

## Обновление индекса

- `python sync.py` — разовый инкрементальный прогон;
- `python sync.py --watch` — следить за хранилищами и переиндексировать на лету (не подходит для хранилищ, смонтированных по NFS/SMB — события файловой системы туда не доходят);
- Linux-сервер: готовые примеры — `brain-sync.service` (демон `--watch`) или `brain-pull.timer` + `brain-pull.service` (раз в 5 минут: `git pull` хранилища + `sync.py`). Установка описана в комментариях внутри файлов.

Установка юнитов (Linux, от root):

```bash
sudo ./install-systemd.sh sync    # brain-sync.service
sudo ./install-systemd.sh pull    # brain-pull.service + brain-pull.timer
sudo ./install-systemd.sh         # все файлы
```

Скрипт копирует файлы в `/etc/systemd/system` и делает `systemctl daemon-reload`; включение и запуск — вручную (`systemctl enable --now ...`). Варианты `sync` и `pull` взаимоисключающие, включайте один.

Индекс — `data/brain.db` (в git не попадает) и полностью пересобирается: после смены схемы или LLM-модели достаточно удалить файл и снова запустить `sync.py`.

## Приватность

Содержимое заметок отправляется в настроенный LLM API. Для чувствительных данных подними локальный сервер (Ollama, LM Studio, vLLM) и укажи его в `LLM_BASE_URL`.

`LLM_BASE_URL` вне `localhost`/`127.0.0.1`/`::1` должен быть HTTPS: по HTTP ключ и текст заметок идут открытым текстом. Для LAN-сервера по HTTP нужно осознанно задать `LLM_ALLOW_HTTP=1` (будет предупреждение в stderr).

## Безопасность

- **Заметки — недоверенные данные.** `search_notes`, `get_chunk` и `get_note` возвращают текст из хранилища; заметка может содержать инструкции для агента (prompt injection). В MCP-клиенте не включай автоподтверждение опасных инструментов и не давай этому серверу лишних прав. Особенно это касается авто-pull’нутых клиппингов и чужих материалов.
- **MCP не аутентифицирует клиента.** Любой процесс, которому разрешён запуск сервера, видит весь индекс. По умолчанию транспорт stdio и сеть не слушается; при запуске по HTTP нужен внешний auth-прокси.
- **Авто-pull хранилища — это доверие к remote.** `brain-pull.timer` и Obsidian Git тянут не только заметки, но и `.mcp.json`, `.obsidian/plugins`; скомпрометированный remote может подменить команду MCP или подсунуть плагин. Для сервера — read-only deploy key/PAT, 2FA и branch protection; не открывай авто-pull’нутое хранилище в клиенте с автозапуском MCP; `.mcp.json` лучше держать вне хранилища или проверять изменения; community plugins — restricted mode.

## Запись из Telegram-бота

MCP-инструмент `create_note(content, request_id)` создаёт **только новые**
Markdown-файлы в `Telegram/` первого хранилища. Существующие заметки не меняются.
Для включения передайте `BRAIN_WRITE_ENABLED=true` в `env` MCP-сервера
в `.mcp.json` (или в окружении процесса). По умолчанию запись выключена, и
`create_note` вообще не регистрируется в списке инструментов (нужен перезапуск
MCP-сервера после смены переменной).
Если конфиг закреплён SHA-256, после изменения обновите пин на стороне клиента.

Клиент обязан проверять права: в KapumChatBot запись доступна только `OWNER_IDS`
в личке через намерение «запомни», выбор после форварда или кнопку под ответом.
Обычная модель чата не получает инструмент записи. Чтение в этом боте открыто
всем пользователям диалога: не подключайте к нему закрытые заметки.

`request_id` — стабильный идентификатор действия клиента (до 200 символов):
повтор с тем же текстом не создаёт дубликат, другой текст с тем же ID отклоняется.
Он должен быть глобально уникальным и содержать namespace пользователя/чата
(например, `tg:<chat_id>:<message_id>`): сервер не аутентифицирует клиента, и
совпадение с чужой записью вернёт конфликт.
Текст ограничен 100000 символами. Имя файла — SHA-256 от request_id, заголовок
индекса — первая строка. Новая заметка сразу индексируется в SQLite/FTS без
платного LLM; обычный sync сохраняет её по тому же content_hash. Если индекс
временно недоступен, файл остаётся для безопасного повтора или последующего sync.
Сохраняется текст/подпись сообщения, не бинарное вложение.

### Автоматическая публикация в Git

После индексации `create_note` коммитит **только созданный файл** и выполняет
обычный push в upstream текущей ветки. Успех возвращается только после push
(`git_pushed=true`). Отдельного переключателя нет: включённая запись требует Git.

Первое хранилище должно быть корнем Git-клона с настроенным upstream. От имени
пользователя MCP-сервера настройте `user.name`, `user.email` и SSH-ключ/credential
helper **с правом записи** в remote (read-only deploy key больше не подходит).
Пароли интерактивно не запрашиваются. Корень хранилища, `.git` и `Telegram/`
должны быть доступны этому пользователю для записи. Секреты не добавляйте в код
или URL remote; используйте SSH/credential helper.

Identity лучше задать **локально в репозитории хранилища**: MCP-процесс в
systemd может не видеть `~/.gitconfig` из-за `ProtectHome=true`.

```bash
sudo -u brain git -C '/opt/brain-vault' config user.name 'Kapum ChatBot'
sudo -u brain git -C '/opt/brain-vault' config user.email 'bot@example.com'
```

Укажите свой GitHub-email или noreply-адрес. Если remote доступен по SSH,
ключ тоже должен быть доступен процессу вне `/home` (например, deploy key в
`/etc/kapum-chatbot/` и `GIT_SSH_COMMAND`), иначе push из MCP не пройдёт
аутентификацию, хотя ручной запуск doctor из обычной оболочки будет успешным.

- Чужие staged/unstaged-файлы не затрагиваются: коммит строится отдельным индексом,
  Git-хуки не запускаются. Пушится точный SHA, только в upstream-ветку, без тегов
  и рекурсивной публикации submodules, без force.
- При наличии посторонних локальных коммитов автоматический push запрещён,
  чтобы не отправить их вместе с заметкой. Сначала разберите их вручную.
- Если remote ушёл вперёд или ветки разошлись, автоматического merge/rebase нет:
  синхронизируйте клон вручную (например, `git pull --ff-only`, если возможен),
  затем повторите исходное сохранение. `brain-pull.timer` продолжает использовать
  fast-forward и не разрешает расхождение истории автоматически.
- При ошибке Git файл и индекс остаются локально. Повтор с тем же `request_id`
  повторяет публикацию без нового файла/коммита; в боте повторите ту же кнопку.
  Уже закоммиченная, но не отправленная заметка тоже корректно отправляется при
  повторе. Пока она не отправлена, сохранение другой заметки не будет пушить её
  попутно: сначала повторите неудавшееся действие.
- Записи одного MCP-процесса сериализованы; смена HEAD другим процессом не
  перезаписывается. Каждый Git-процесс ограничен 60 секундами; таймаут записи
  в Telegram-клиенте — не менее 180 секунд.

Ошибки Git содержат название стадии и безопасную категорию: например,
`Ошибка Git (commit-tree): не настроены user.name/user.email` или
`Ошибка Git (fetch): сбой DNS Git`. Полный stderr не возвращается: он может
содержать credentials в remote URL и приватные пути. Клиент KapumChatBot
распознаёт эти категории и добавляет подсказку в traceback; для этого нужно
обновить обе стороны и перезапустить MCP-процесс.

Не включай `BRAIN_WRITE_ENABLED=true` для MCP-профиля общего чата или модели,
которая видит недоверенные заметки: prompt injection может инициировать запись.
Права проверяет клиент.

### Проверка готовности записи

На сервере запустите скрипт **тем же пользователем и с теми же переменными**,
что у MCP-сервера (особенно `VAULT_PATH` и `BRAIN_WRITE_ENABLED`):

```bash
cd /opt/ObsidianBrain
BRAIN_WRITE_ENABLED=true .venv/bin/python write_doctor.py
# при необходимости проверить доступ к remote:
BRAIN_WRITE_ENABLED=true .venv/bin/python write_doctor.py --network
```

Скрипт проверяет флаг записи, права на хранилище/`Telegram`/SQLite/`.git`,
корень Git-репозитория, ветку, upstream, `user.name`/`user.email`, staged-файлы,
отставание клона от upstream и локальные коммиты. `--network` делает `git fetch`
и показывает, если клон отстал или ветки разошлись; автоматический merge/rebase
не выполняется. Секреты, remote URL и заметки не печатаются.
Если `.mcp.json` задаёт `BRAIN_WRITE_ENABLED` только для MCP-процесса, doctor
запускайте с этой переменной явно.

Проверка на временных файлах без `.env`, LLM и реального хранилища:
`python -m unittest discover -s tests -v`.
